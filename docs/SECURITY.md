# VERIFAI — Security Architecture & Vulnerability Policy

**Version:** 1.0.0-rc  
**Last Updated:** October 2026  

---

## 1. Security Philosophy & Principles

VERIFAI is engineered under the principle that sensitive academic, financial, and personal credentials must remain strictly protected at rest, in transit, and during evaluation. The platform enforces:

1. **Zero-Trust Document Vault**: Cleartext document data is never written to persistent disks.
2. **Cryptographic User Isolation**: Encryption keys are derived per user, ensuring compromised storage does not yield cross-user plaintexts.
3. **Data Minimization by Default**: Verifiers receive only the minimum factual subset required to validate eligibility.
4. **Defense-in-Depth**: Layered protection combining cryptographic primitives, ORM parameterization, schema validation, and audit logging.

## 2. Cryptographic Architecture

The platform's cryptographic implementation is contained in [`backend/app/core/crypto.py`](../backend/app/core/crypto.py) and [`backend/app/core/security.py`](../backend/app/core/security.py) using the industry-standard `cryptography.hazmat` and `argon2-cffi` libraries.

### 2.1 Symmetric Encryption (AES-256-GCM)
- **Algorithm**: Advanced Encryption Standard in Galois/Counter Mode (AES-GCM).
- **Key Length**: 256 bits (32 bytes).
- **Nonce (IV)**: 96 bits (12 bytes) generated per encryption operation via `os.urandom(12)`. Nonce reuse is strictly prohibited.
- **Authentication Tag**: 128 bits (16 bytes) generated by GCM to guarantee both confidentiality and cryptographic integrity.
- **Ciphertext Format**:
  $$\text{Payload} = \text{Nonce (12 bytes)} \parallel \text{Ciphertext} \parallel \text{Tag (16 bytes)}$$
- **Tampering Detection**: The decrypt routine verifies the authentication tag prior to releasing plaintext. Any modification raises an explicit `ValueError("Ciphertext tampering detected or invalid key.")`.

### 2.2 Key Derivation Function (HKDF-SHA256)
Individual user vault keys are not stored in the database. Instead, they are deterministically derived on-demand from the application master key and the user's immutable UUID:
$$\text{UserVaultKey} = \text{HKDF}(\text{algorithm}=\text{SHA-256}, \text{length}=32, \text{salt}=\text{UUID}.\text{bytes}, \text{info}=b"\text{verifai-user-vault}", \text{key}=\text{MasterKey})$$

**Benefits**:
- If the relational database is dumped without the master key, no documents can be decrypted.
- If an individual derived key is compromised, other users' vaults remain secure.

### 2.3 Password Hashing (Argon2id)
All user passwords are encrypted using the winner of the Password Hashing Competition, **Argon2id**:
- **Library**: `argon2-cffi`
- **Variant**: Argon2id (hybrid defense against both side-channel and GPU/ASIC attacks)
- **Parameters**: Default high-work memory factor (65,536 KiB), time factor (3 iterations), and parallelism (4 lanes).
- **Storage**: Passwords are never logged or stored in reversible format.

### 2.4 Token Authentication (JWT)
- **Standard**: JSON Web Token (RFC 7519)
- **Algorithm**: HMAC with SHA-256 (`HS256`)
- **Payload**: Contains `sub` (user UUID), `email`, and `exp` (UTC timestamp).
- **Lifecycle**: Configurable expiration via `ACCESS_TOKEN_EXPIRE_MINUTES` (default 60 minutes).

## 3. Threat Mitigation Matrix

| Threat Category | Potential Attack Vector | Applied Mitigation in VERIFAI |
| :--- | :--- | :--- |
| **Data Leak at Rest** | Unauthorized access to filesystem storage volume | Blobs are encrypted with AES-256-GCM. Without `VAULT_MASTER_KEY_HEX`, files appear as high-entropy pseudorandom data. |
| **SQL Injection** | Malicious SQL fragments in input parameters | SQLAlchemy 2.0 ORM uses parameterized queries exclusively; no raw string concatenation is used in query building. |
| **Path Traversal** | Manipulated upload filenames (`../../etc/passwd`) | Uploaded files are assigned synthetic UUID filenames on disk; original filenames are stored purely as metadata in database columns. |
| **Ciphertext Tampering** | Bit-flipping attacks on encrypted files | GCM 128-bit authentication tag ensures immediate failure upon any byte alteration. |
| **Over-Disclosure** | Verifiers demanding complete transcript to verify a single GPA requirement | Selective disclosure policy engine filters claims, generating a redacted presentation package with user consent. |
| **Credential Stuffing** | Automated brute-force login attempts | Argon2id high memory cost throttles offline cracking; production deployment guidelines mandate rate-limiting proxies. |

## 4. Key Management & Rotation

### 4.1 Master Key Management
- The `VAULT_MASTER_KEY_HEX` environment variable must be a 64-character hexadecimal string (32 bytes).
- **Generation**:
  ```bash
  python -c "import secrets; print(secrets.token_hex(32))"
  ```
- **Production Environments**: Master keys should be provisioned via a Hardware Security Module (HSM), AWS Secrets Manager, HashiCorp Vault, or Google Cloud Secret Manager.

### 4.2 Key Rotation Procedure
To rotate the vault master key without data loss:
1. Spin up a migration worker provisioned with both `OLD_VAULT_MASTER_KEY` and `NEW_VAULT_MASTER_KEY`.
2. Iterate through all document records:
   - Decrypt document blob using old derived key.
   - Encrypt document blob using new derived key.
   - Overwrite blob in vault storage.
3. Update server configuration with `NEW_VAULT_MASTER_KEY` and deprecate the old key.

## 5. Security Recommendations for Production Deployment

For enterprise deployments outside educational and local testing environments:
1. **HTTP-Only Cookies**: Migrate JWT storage from client `localStorage` to `HttpOnly`, `Secure`, `SameSite=Strict` cookies to defend against Cross-Site Scripting (XSS).
2. **Reverse Proxy & TLS**: Place the FastAPI backend behind an NGINX, Cloudflare, or Envoy reverse proxy with TLS 1.3 and HSTS enabled.
3. **Rate Limiting**: Enable IP-based and user-based rate limits on `/api/v1/auth/login` and `/api/v1/vault/upload` to prevent Denial-of-Service and brute-force abuse.
4. **Merkle Audit Trail**: Upgrade the relational audit log table to a cryptographically anchored Merkle tree to provide non-repudiation guarantees.

## 6. Vulnerability Disclosure Policy

If you discover a security vulnerability in VERIFAI, please notify the maintainers responsibly:
- **Do NOT file a public GitHub issue.**
- Submit your finding privately via GitHub Security Advisories or email the project security team.
- Provide detailed steps to reproduce the vulnerability, including sample requests, environment details, and affected components.
- Maintainers commit to acknowledging reports within 48 hours and providing a remediation timeline.
